Cours bonus

Ce cours est hors programme du BTS : il ne compte ni dans ta progression ni au classement. Il est là pour aller plus loin.

L'équipe bleue (*blue team*) construit et défend. Face aux cinq failles du chapitre précédent, elle n'ajoute pas un gadget de sécurité par-dessus : elle écrit le code autrement. Ce chapitre donne les cinq correctifs, puis les principes qui les dépassent. Tu les écriras toi-même dans l'atelier de code, côté défense.

1. La défense en profondeur

Aucune protection n'est parfaite : on en empile plusieurs, indépendantes, pour que la chute de l'une n'ouvre pas tout. Autour d'un formulaire : le client aide l'utilisateur (confort), mais le serveur revérifie tout (sécurité) ; la base n'a que les droits utiles ; les secrets sont dans un coffre ; les accès sont journalisés. Si le filtre d'entrée est contourné, la requête préparée tient encore ; si elle tombe, les droits limités réduisent les dégâts.

2. Les cinq correctifs

Injection SQL → la requête préparée. On ne fabrique plus de texte de requête. On envoie une requête à trous et les valeurs à part : elles ne peuvent plus être prises pour du code.

// Au lieu de coller les valeurs, on les compare (idée de la requête préparée)
var MEMBRES = [{ id: "admin", mdp: "secret-admin" }, { id: "lea", mdp: "lea2026" }];
function connexion(identifiant, motdepasse) {
  for (var i = 0; i < MEMBRES.length; i++)
    if (identifiant === MEMBRES[i].id && motdepasse === MEMBRES[i].mdp) return MEMBRES[i].id;
  return null;
}
console.log(connexion("lea", "lea2026"));        // lea
console.log(connexion("admin' --", "x"));        // null : l'injection ne veut plus rien dire

XSS → l'encodage de sortie. On échappe les caractères spéciaux au moment de l'affichage : < devient &lt;, etc. La balise devient du texte inoffensif.

function echapper(s) {
  return String(s)
    .replace(/&/g, "&amp;").replace(/</g, "&lt;").replace(/>/g, "&gt;")
    .replace(/"/g, "&quot;").replace(/'/g, "&#39;");
}
console.log(echapper("<img src=x onerror=alert(1)>"));
console.log(echapper("Bonjour Léa"));

Contrôle d'accès → la vérification côté serveur. On ne croit jamais un rôle ou un identifiant envoyé par le client. L'identité vient du jeton de session ; le rôle, d'une table côté serveur ; et on vérifie que la ressource demandée appartient bien à l'utilisateur.

Traversée de répertoire → la liste blanche. On refuse tout nom contenant /, \ ou .., ou mieux, on n'accepte qu'une liste de noms connus.

function nomSur(nom) {
  if (/[\/\\]/.test(nom) || nom.indexOf("..") >= 0) return null;
  return nom;
}
console.log(nomSur("photo.png"));            // photo.png
console.log(nomSur("../../etc/passwd"));     // null

Injection de commande → ne pas construire de commande. On évite le shell ; si c'est impossible, on n'accepte qu'une liste blanche de caractères et on passe les arguments séparément, jamais dans une chaîne concaténée.

3. Valider : liste blanche, pas liste noire

Interdire « les mauvais caractères » (liste noire) échoue toujours : on en oublie, l'attaquant trouve l'oubli. N'autoriser que ce qui est prévu (liste blanche) est bien plus sûr : un entier est un entier, un nom de fichier ne contient que des lettres et des chiffres, un tri ne peut valoir que nom, prix ou date.

function triValide(tri) {
  var autorises = ["nom", "prix", "date"];
  return autorises.indexOf(tri) >= 0 ? tri : "nom";   // sinon, valeur par défaut
}
console.log(triValide("prix"));                 // prix
console.log(triValide("prix; DROP TABLE t"));   // nom : tout ce qui n'est pas prévu est rejeté

4. Détecter et se préparer

Empêcher ne suffit pas : il faut voir quand ça rate. On journalise les événements de sécurité (connexions, échecs, accès refusés), on centralise et on alerte (SIEM), on surveille les comportements anormaux. Et on se prépare à l'incident avant qu'il arrive : sauvegardes hors ligne testées, procédure de réponse écrite, rôles connus. Une faille finira par passer ; ce qui distingue une entreprise, c'est la vitesse à laquelle elle la détecte et y répond.

À toi de défendre

Dans l'atelier de code, tu reçois une attaque qui marche, et tu dois réécrire la fonction pour qu'elle la bloque — ainsi que ses variantes — sans casser l'usage normal. C'est exactement le geste du développeur sécurisé.
