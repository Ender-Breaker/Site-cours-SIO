=== git-bases | Git : enregistrer l'histoire d'un projet | f
**Git** est un logiciel de **gestion de versions** : il enregistre l'histoire d'un projet, étape par étape. Il permet de revenir en arrière, de travailler à plusieurs sans s'écraser, et de savoir qui a changé quoi et pourquoi. C'est l'outil le plus demandé en stage, en SLAM comme en SISR (scripts, configurations, documentation) : il est attendu dans ton portfolio de l'épreuve E5.

!info Git n'est pas GitHub | **Git** est le logiciel, installé sur ta machine. **GitHub** (comme GitLab) est un site qui héberge des dépôts Git et ajoute des outils de collaboration.

## 1. Installer et se présenter

```
git --version                                   # vérifie l'installation
git config --global user.name "Léa Martin"      # à faire une seule fois
git config --global user.email "lea@exemple.fr"
git config --global init.defaultBranch main
```

Ton nom et ton adresse sont inscrits dans chaque enregistrement que tu fais.

## 2. Les trois zones

| Zone | Contenu | Commande pour y entrer |
| Répertoire de travail | tes fichiers, tels que tu les modifies | (ton éditeur) |
| Index (*staging area*) | ce qui partira dans le prochain commit | `git add` |
| Dépôt (dossier caché `.git`) | l'historique des commits | `git commit` |

Un **commit** est une photographie complète du projet à un instant donné, avec un auteur, une date, un message et un identifiant unique (un *hash* comme `a1b2c3d`).

## 3. Le cycle de base

```
mkdir mon-site && cd mon-site
git init                         # crée le dépôt (dossier .git)
git status                       # où en est-on ? À taper sans modération

# … on crée index.html …
git add index.html               # place le fichier dans l'index
git add .                        # … ou tout ce qui a changé
git commit -m "Ajoute la page d'accueil"

git log                          # l'historique complet
git log --oneline                # une ligne par commit
```

```
$ git status
Sur la branche main
Modifications qui ne seront pas validées :
        modifié :         index.html
Fichiers non suivis :
        style.css
```

## 4. Voir ce qui a changé

```
git diff                 # modifications pas encore ajoutées à l'index
git diff --staged        # ce qui est dans l'index, prêt à être commité
git show a1b2c3d         # le contenu d'un commit précis
git log -p index.html    # l'histoire d'un fichier, avec les modifications
```

## 5. Ignorer des fichiers : `.gitignore`

Certains fichiers ne doivent **jamais** être versionnés : mots de passe, dépendances téléchargées, fichiers générés.

```
# fichier .gitignore à la racine du projet
.env                 # secrets, mots de passe
node_modules/        # dépendances (se réinstallent)
vendor/
target/
*.log
.vscode/
```

!attention Jamais de secret dans Git | Un mot de passe ou une clé d'API commité reste dans l'historique **même si tu le supprimes ensuite**. S'il a été poussé sur GitHub, il faut le considérer comme volé et le changer immédiatement. Mets les secrets dans un fichier `.env` listé dans `.gitignore`.

## 6. De bons messages de commit

Un commit = **un changement cohérent**. Son message dit **ce que le commit fait**, au présent, en une ligne courte.

| À éviter | À écrire |
| `modifs` | `Corrige le calcul de la TVA` |
| `ça marche enfin` | `Ajoute la validation du formulaire de contact` |
| `v2 finale ok` | `Supprime le script de sauvegarde obsolète` |

=== git-branches | Git : les branches et les fusions | m
Une **branche** est une ligne de développement indépendante. Elle permet de travailler sur une fonctionnalité ou une correction sans toucher à la version qui marche. Créer une branche est instantané : c'est juste une étiquette posée sur un commit.

## 1. Créer et changer de branche

```
git branch                       # liste les branches ; * marque la branche courante
git switch -c contact            # crée la branche « contact » et s'y place
git switch main                  # revient sur main
git branch -d contact            # supprime une branche déjà fusionnée
```

`git checkout -b contact` est l'ancienne écriture de `git switch -c contact` : tu la verras partout.

**HEAD** désigne « là où tu es » : la branche courante et son dernier commit.

## 2. Travailler sur une branche

```
git switch -c formulaire-contact
# … on modifie contact.html …
git add .
git commit -m "Ajoute le formulaire de contact"
git log --oneline --graph --all          # dessine l'arbre des branches
```

Pendant ce temps, `main` n'a pas bougé : si un bug urgent arrive, on y revient, on le corrige, et la fonctionnalité en cours reste à l'abri sur sa branche.

## 3. Fusionner : `git merge`

On se place sur la branche qui **reçoit**, et on fusionne l'autre.

```
git switch main
git merge formulaire-contact
```

| Cas | Ce que fait Git |
| `main` n'a pas avancé depuis la création de la branche | *fast-forward* : l'étiquette `main` avance simplement |
| les deux branches ont avancé | un **commit de fusion** réunit les deux histoires |
| les deux ont modifié les mêmes lignes | **conflit** : Git s'arrête et te demande de trancher |

## 4. Résoudre un conflit

```
$ git merge formulaire-contact
CONFLIT (contenu) : Conflit de fusion dans index.html
La fusion automatique a échoué ; réglez les conflits et validez le résultat.
```

Git a marqué la zone en conflit dans le fichier :

```
<<<<<<< HEAD
<h1>Bienvenue sur mon site</h1>
=======
<h1>Bienvenue sur le portfolio de Léa</h1>
>>>>>>> formulaire-contact
```

1. Ouvre le fichier et **choisis** ce qu'il faut garder (une version, l'autre, ou un mélange).
2. Supprime les trois lignes de marqueurs `<<<<<<<`, `=======`, `>>>>>>>`.
3. `git add index.html` puis `git commit` pour terminer la fusion.

`git merge --abort` annule tout et revient à l'état d'avant la fusion. Un conflit n'est pas une erreur : c'est Git qui refuse de deviner à ta place.

## 5. Une méthode de travail simple

- `main` contient toujours une version **qui fonctionne**.
- Une branche par tâche, avec un nom explicite : `correction-menu-mobile`, `ajout-page-contact`.
- Des commits petits et fréquents.
- On fusionne dans `main` quand la tâche est terminée et testée, puis on supprime la branche.

=== git-github | Git : GitHub et le travail en équipe | m
Un **dépôt distant** (*remote*) est une copie du dépôt hébergée sur un serveur : GitHub, GitLab ou le serveur de ton entreprise. C'est lui qui permet de sauvegarder, de partager et de collaborer.

## 1. Relier son dépôt à GitHub

```
git remote add origin https://github.com/lea/portfolio.git    # « origin » : nom donné au distant
git remote -v                                                 # vérifie
git push -u origin main          # premier envoi ; -u mémorise le lien
git push                         # les fois suivantes
```

Pour récupérer un projet existant, une seule commande :

```
git clone https://github.com/lea/portfolio.git
```

## 2. Envoyer et recevoir

| Commande | Effet |
| `git push` | envoie tes commits vers le distant |
| `git fetch` | télécharge les nouveautés **sans** modifier tes fichiers |
| `git pull` | `fetch` puis fusion : met ta branche à jour |
| `git clone` | copie un dépôt distant complet |

```
git pull                         # avant de commencer à travailler
# … commits …
git push                         # quand une étape est terminée
```

!attention `push` refusé | Si quelqu'un a poussé avant toi, Git refuse ton `push` : fais d'abord `git pull`, règle un éventuel conflit, puis `git push`. N'utilise **jamais** `git push --force` sur une branche partagée : tu écraserais le travail des autres.

## 3. S'authentifier

GitHub n'accepte plus les mots de passe en ligne de commande. Deux solutions :

- une **clé SSH** : `ssh-keygen -t ed25519`, puis on colle la clé **publique** (`~/.ssh/id_ed25519.pub`) dans les réglages de GitHub. L'adresse du dépôt devient `git@github.com:lea/portfolio.git` ;
- un **jeton d'accès personnel** (*token*) utilisé à la place du mot de passe en HTTPS.

## 4. La pull request

Sur un projet d'équipe, personne ne pousse directement sur `main`. On propose ses modifications dans une **pull request** (PR ; *merge request* sur GitLab).

1. Créer une branche et y commiter : `git switch -c correction-menu`.
2. La pousser : `git push -u origin correction-menu`.
3. Sur GitHub, ouvrir une pull request vers `main` : titre, description, captures.
4. Un coéquipier **relit** le code, commente, demande des changements.
5. Quand c'est validé, on **fusionne** la PR, puis on supprime la branche.

La relecture attrape les bugs, diffuse les connaissances dans l'équipe, et laisse une trace écrite des décisions.

## 5. Fork, issues et le reste

| Outil | Rôle |
| *Fork* | ta copie personnelle du dépôt de quelqu'un d'autre, pour proposer une contribution |
| *Issue* | un ticket : bug à corriger, idée, tâche |
| `README.md` | la page d'accueil du dépôt, en Markdown |
| *Releases* / tags | les versions publiées (`git tag v1.0`) |
| GitHub Actions | automatisation : tests et déploiement à chaque `push` |
| GitHub Pages | hébergement gratuit d'un site statique |

## 6. Un bon README

Le README est la première chose que voit un recruteur ou un jury sur ton dépôt. Il s'écrit en **Markdown** :

```
# Gestion de parc informatique

Application web de suivi du matériel (projet de BTS SIO).

## Fonctionnalités
- Inventaire du matériel
- Suivi des interventions

## Installation
1. `git clone https://github.com/lea/parc.git`
2. `composer install`
3. Copier `.env.exemple` en `.env` et renseigner la base de données

## Technologies
PHP 8, MariaDB, Bootstrap
```

=== git-annuler | Git : annuler, corriger et bonnes pratiques | m
Git ne perd presque jamais rien : il existe une commande pour chaque situation. L'important est de savoir **où** se trouve ce qu'on veut annuler.

## 1. Quelle commande pour quelle situation ?

| Situation | Commande |
| J'ai modifié un fichier et je veux retrouver la version du dernier commit | `git restore fichier` |
| J'ai fait `git add` par erreur | `git restore --staged fichier` |
| Mon dernier message de commit est faux | `git commit --amend -m "Nouveau message"` |
| J'ai oublié un fichier dans le dernier commit | `git add fichier` puis `git commit --amend --no-edit` |
| Je veux annuler un commit déjà poussé | `git revert a1b2c3d` |
| Je veux défaire mes derniers commits **locaux** | `git reset` |

!attention `git restore fichier` est définitif | Les modifications non commitées qu'il efface ne sont enregistrées nulle part : elles sont perdues pour de bon.

## 2. `revert` ou `reset` ?

```
git revert a1b2c3d           # crée un NOUVEAU commit qui annule a1b2c3d
```

`revert` n'efface rien : il ajoute un commit inverse. C'est la seule méthode correcte pour un commit **déjà partagé**.

```
git reset --soft HEAD~1      # défait le dernier commit, garde les changements dans l'index
git reset HEAD~1             # défait le dernier commit, garde les changements dans les fichiers
git reset --hard HEAD~1      # défait le dernier commit ET efface les changements
```

`reset` réécrit l'histoire : à réserver aux commits qui n'ont **pas encore été poussés**. `HEAD~1` signifie « un commit avant HEAD ».

## 3. Mettre de côté : `git stash`

Tu es au milieu d'une modification et il faut changer de branche tout de suite :

```
git stash                    # range les modifications en cours, le dossier redevient propre
git switch main              # … on corrige l'urgence …
git switch ma-branche
git stash pop                # reprend là où on en était
git stash list               # ce qui est en attente
```

## 4. Retrouver un commit « perdu »

```
git reflog                   # le journal de tous les déplacements de HEAD
git switch -c sauvetage a1b2c3d      # recrée une branche sur le commit retrouvé
```

Même après un `reset --hard`, le commit reste récupérable pendant plusieurs semaines grâce à `reflog`.

## 5. Enquêter

```
git log --oneline --author="Léa" --since="2 weeks ago"
git log -S "motDePasse"              # commits qui ont ajouté ou retiré ce texte
git blame config.php                 # qui a écrit chaque ligne, et dans quel commit
git bisect start                     # recherche du commit qui a introduit un bug
```

## 6. Les étiquettes de version

```
git tag v1.0                         # marque le commit courant
git tag                              # liste
git push origin v1.0                 # les tags se poussent explicitement
```

La numérotation habituelle est **majeur.mineur.correctif** : `2.4.1`. On incrémente le correctif pour un bug, le mineur pour une nouveauté compatible, le majeur pour un changement incompatible.

## 7. Les bonnes pratiques

- `git status` avant chaque `add`, `commit` et `push`.
- `git pull` avant de commencer à travailler.
- Des commits petits, un sujet par commit, un message clair.
- Une branche par tâche ; `main` toujours fonctionnelle.
- Un `.gitignore` dès le premier commit ; aucun secret dans le dépôt.
- Ne jamais réécrire une histoire déjà partagée (`reset`, `amend`, `push --force`).

!info Pour les SISR aussi | Scripts d'administration, fichiers de configuration (`nginx.conf`, règles de pare-feu), playbooks Ansible, documentation : tout ce qui est du texte gagne à être versionné. C'est le principe de l'*infrastructure as code* : on sait ce qui a changé sur un serveur, quand, et par qui.
